# V11.1 — BBS beam ordering implementation

Presentation-layer only. No detection, matching, Vision, or engineering-formula changes.

---

## Current ordering problem

The AI BBS listed beam groups in a different sequence from the Estimator Computed Output Sheet. Estimator sheets follow the reinforcement drawing: visual row (top → bottom), and within each row left → right.

That made line-item comparison mix **ordering differences** with estimation differences.

## Previous ordering source

Not drawing layout.

1. R.1.3 builds `models` with `sorted(r1_models.items())` — **lexicographic beam ID** (`B1`, `B10`, `B11`, … before `B2` / `B5`).
2. VB.1 steel weights iterate that model list as-is.
3. `BBSCompletionEngine.generate()` emits one beam group per `summary.beam_weights` entry, in that same list order.
4. Excel BBS writes `bbs_rows` sequentially.

So the previous BBS order was **dictionary/ID sort inherited from R.1.3**, not DXF entity order and not drawing rows.

Upstream model order is **unchanged**. Only the final BBS list is reordered.

## New ordering source

Existing VROOT1 `beam_registry.json` centroids (`centroid_x`, `centroid_y`) from reinforcement-drawing text clusters.

Fallback if a beam is missing from VROOT1: L.2.2 `geometry_registry.json` `dxf_centroid_x/y`, then `dxf_bbox` / `bounding_box` center.

No new geometry calculation. No hardcoded beam IDs.

## Beam spatial-position method

Representative position = existing centroid of the beam mark on the reinforcement drawing.

Recorded in the VB.1 artefact `bbs_beam_order_trace.json`.

## Row-grouping method

1. Sort located beams by visual Y (top first), then X.
2. Split into rows where consecutive visual-Y drop exceeds a **scale-aware threshold**:
   - If Y-gaps are bimodal (`max/median >= 4`): treat the small mode as within-row jitter (`tau = max(8×median, 0.15×(median+max))`).
   - Else if the cloud is much wider than tall (`y_span <= 0.20 × x_span`): one row.
   - Else: `tau = 0.5 × max_gap` (split large drops; equal vertical stacks stay separate rows).
3. Identical input → identical rows (deterministic).

## Left-to-right sorting

Within each row: sort by `centroid_x` ascending, then `beam_id` as a last-resort tie-breaker only.

## Coordinate-system handling

Verified from `PhaseM.1_engineering_vision_dataset/dxf_renderer.py` `CoordTransform`:

- DXF **X increases right**
- DXF **Y increases up**
- Image Y is flipped for pixels; **BBS ordering uses DXF**, so visual top = **larger Y**

`y_increases_visually_up=False` is supported for tests / inverted conventions and is not used in production DXF.

## Within-beam preservation

Each beam’s existing BBS rows move as a contiguous group. Line-item order inside the group is unchanged.

Header `si_no` is renumbered 1…N after the move (presentation index only).

## Fallback handling

If a BBS beam has no usable centroid/bbox:

- coordinates are **not** invented
- engineering values are **not** changed
- the beam group is **appended after** spatially ordered beams, in original encounter order
- the condition is logged and listed in `bbs_beam_order_trace.json`

If **no** beam has geometry, the original BBS order is kept (`ORIGINAL_ENCOUNTER_ORDER_NO_GEOMETRY`).

Disable the layer: `STEEL_BBS_SPATIAL_ORDER=off`.

## Invariants

Checked in `assert_bbs_invariants` before Excel write:

- same BBS row count
- same beam membership
- same within-beam row sequence
- same row multiset excluding `si_no` (quantities, diameters, lengths, weights)

## Known limitations

- **Beam Summary** (and other non-BBS sheets) still follow L.2 / lexicographic model order. This phase reorders **BBS only**.
- Centroids are **beam-mark** positions, not framing-plan polylines. Two detail blocks at similar drawing Y are one visual row (left group then right group), which matches estimator-style sheet reading.
- Full live Hybrid Excel replay was not run (would write a complete estimate and is out of this ordering-only phase). Galera validation uses stored VROOT1 centroids from that drawing.
